# Implementer protocol

All five candidates are queued. Publication creates delivery scaffolding in the eventual product repositories; it does not activate implementation or demonstrate a working product. Relative months start only at explicit activation. The first functional public result must occur between months 3 and 12.

## Capacity and activation
Use one 16-hour weekly allocation across the portfolio, including other product work the owner has activated. At most one active project and one implementation issue may be In Progress. Before activation, inspect the owner's other delivery Projects and resolve any competing active commitment. Record the selected slug and activation date in the portfolio registry. Start/Target dates stay blank until a real schedule is agreed.

## Issue execution
1. Read the repository README, docs/EXECUTION_PLAN.md and the matching stable task in planning/backlog.json. Inspect the live issue for newer accepted scope.
2. Verify activation, WIP capacity, completed dependencies and the milestone's data/rights gates. Keep a blocked dependency queued; record the precise blocker and next feasible action.
3. Create a branch for the bounded issue. Follow its outputs and acceptance checks. If work exceeds its estimate or changes scope, evaluation, rights or architecture, record the decision and re-plan remaining hours before expanding.
4. Retain commands, input hashes, seeds, versions, resource measurements, test results and failure cases. Keep measured evidence separate from planned targets and synthetic evidence separate from real-world evidence.
5. Submit a pull request linking the issue. Move to In Review only with reviewable outputs. Done requires all acceptance checks plus documented review and merge; for non-code work, use a reviewed documentation PR. A second agent may review, but disclose that it is automated review.
6. If blocked, move to Blocked with the failed check, evidence, missing prerequisite and smallest next action; dependent tasks remain Todo. Never close tasks because their plan or issue has been published.

## Data, models and compute
Use scriptable public data with compatible rights or deterministic synthetic generation. Manual collection, labeling and per-example curation are outside scope. Failure inspection and optional workflow feedback are permitted. Record licenses for data, model weights, fonts, dependencies and derived outputs independently. Unresolved or noncommercial rights block commercial-path use; use the planned permitted fallback where available.
Fit the GTX 1650 Ti 4GB and 16GB RAM through a measured smoke benchmark before scaling. No paid cloud, data or API is authorized. Free hosted compute is optional and cannot be a critical dependency.

## Product gates and tracking
Public benchmark performance establishes technical evidence; customer value remains unvalidated until independently observed. Optional trials require separate participation and data consent, not manual dataset creation. Never label an unvalidated tool production-ready or imply self-directed work was employment.
GitHub issues/Projects hold live status; backlog.json holds stable technical contracts. Synchronize accepted scope changes by PR and preserve stable task IDs. At each milestone compare actual hours with remaining reserve and record continue, reduce, or stop.
Astra/high owns planning reviews; Luna/medium owns conservative tracking/publication. One GitHub writer reconciles remote state before any create, saves receipts immediately, and stops on ambiguous writes. Re-running an importer must preserve later human progress.
No recurring monitor is enabled. No outbound messages to people, spending, destructive cleanup or product implementation are authorized by plan publication.
